# Target architecture proposal

This is a proposed target instant, expressed in the present tense of that target.
It is not a report of implemented behavior.
Every section carries its own maturity and decision authority.
The [vision](../VISION.md) holds purpose, and [captured intent](project-intent.md) distinguishes user direction from design inference.
The [CLI-002 implementation record](authoring/CLI-002.md) identifies the implemented authoring subset and its measured acceptance results; broader sections below retain their stated proposal status.
The [CLI-003 record](composition/CLI-003.md) adds bounded authored definitions, explicit activation, contextual discovery, and simulated bindings. The [CLI-004 record](constraints/CLI-004.md) adds explicit schema snapshots, contextual guidance, and constrained authoring; broader reuse and connected execution remain proposals.
The [CLI-005 experiment](reuse/CLI-005.md) prepares whole-checkpoint reuse and a separately evaluated continuation using the existing runtime.
General component composition and fresh-actor evidence remain open; the trial tooling does not add a kernel layer or definition format.

## Identity and scope

**Maturity: provisional.**

The system interprets a loaded definition as a contextual CLI.
Its interaction derives from declared operations, structured state, constraints, and explicit behavior bindings.
Structured authoring is independently useful and also constructs definitions for that runtime.

The system does not invent domain functionality from a verb name, infer authority from a definition, or treat a saved document as an observation of an external system.
The ownership tree of a JSON document and the graph of relationships in a modeled system are distinct structures.

## Justification chain

**Maturity: provisional.**

### Domain

The domain is contextual construction and use of structured interfaces by people and agents.
The defining need is preservation of meaning through construction, composition, execution, and transfer to another actor.

### Axioms

| Anchor | Commitment relevant to this shape |
|---|---|
| [A3: sovereign composition](https://github.com/apnex/mission-kit/blob/main/axioms/A3-sovereign-composition.md) | Each concern has an explicit boundary; stable public surfaces require real consumers. |
| [A4: zero-loss knowledge](https://github.com/apnex/mission-kit/blob/main/axioms/A4-zero-loss-knowledge.md) | Source intent, exact definitions, rationale, and evidence remain recoverable. |
| [A5: perceptual parity](https://github.com/apnex/mission-kit/blob/main/axioms/A5-perceptual-parity.md) | Human and agent presentations expose equivalent relevant meanings and observations. |
| [A7: resilient agentic operations](https://github.com/apnex/mission-kit/blob/main/axioms/A7-resilient-agentic-operations.md) | Interrupted or failed work has observable state and actionable outcomes. |
| [A11: cognitive minimalism](https://github.com/apnex/mission-kit/blob/main/axioms/A11-cognitive-minimalism.md) | Declared mechanical rules are interpreted deterministically rather than reconstructed by an agent. |

### System north star

One declared operation model determines discoverable choices and execution meaning while retaining enough explicit state and evidence for another actor to continue.

### Principles

- Structured documents remain useful without a project-specific CLI definition.
- A schema has an explicit role as authored data or as an active constraint.
- The CLI definition records operation meaning and dependencies once.
- Definition editing and definition activation have distinct boundaries.
- A mock is an explicit binding state with distinguishable results.
- Document acceptance and evidence of external effects are separate claims.
- A modeled system carries explicit relationships rather than relying on tree location to explain every dependency.
- Human and machine presentations share dispatch semantics.
- Specification size remains separate from the value of its construction workflow.

The [verbs-as-data pattern](https://github.com/apnex/mission-kit/blob/main/patterns/P5-verbs-as-data-surface.md) grounds the shared operation model.
Its handler-completeness rule is scoped here to bindings that claim implemented behavior.
Declared and mocked operations are legitimate states in the owner's requested workflow, and their state is explicit.

### Design choices and their authority

The responsibility boundaries in the following model are author proposals derived from the principles above.
They are not ratified public APIs, crate boundaries, or process boundaries.
The owner authorized the initial scaffold and subsequently selected CLI-001, CLI-002, and [CLI-003](context/cli-003-approval.json).
The [first authoring decision](authoring/CLI-001.md#decision-0001-establish-the-bounded-authoring-contract) establishes the bounded engineering contract for CLI-002; it does not ratify the full decomposition as public APIs.

### Model

The anchored core below gives each responsibility a named scope, declared dependencies, and a reason for its boundary.
The directory structure makes those proposals inspectable without selecting their implementation packaging.
Layer documentation lives under `docs/layers/`; the first application uses one unpublished Rust package with internal responsibilities.

## Entity model and interfaces

**Maturity: conceptual model, with a concrete first authoring contract.**

| Entity | Meaning | Required distinction |
|---|---|---|
| Document | Structured values with explicit identity and locations. | An object key is not inferred to be an array index from its spelling. |
| Authoring session | Working context, draft, accepted baseline, pending changes, and relevant revision references. | A current prompt is a presentation of session state. |
| Constraint attachment | A selected schema, its interpretation, and its reference context. | Schema content being edited is distinct from schema content governing an edit. |
| CLI definition | Contexts, operations, input and output expectations, relationships, dependencies, and behavior references. | JSON ownership and modeled entity relationships are distinct. |
| Operation binding | The relationship between a declared operation and available behavior. | Unbound, simulated, and connected behavior have different meanings. |
| Invocation record | A request's definition identity, inputs, relevant state, outcome, and effect evidence. | Acceptance, simulation, execution, and observed consequence are different observations. |
| Resumption context | References to original intent, definitions, drafts, constraints, unresolved questions, and evidence. | Declared knowledge and externally observed state retain their provenance. |

These are conceptual entities, not a published serialization schema.
The dependency registry states what each responsibility consumes and exposes at this altitude.
The [authoring contract](authoring/SESSION-CONTRACT.md) specifies the first slice's typed paths, session checkpoint, revision fields, operation requests, and results.
The [bootstrap declaration](authoring/operations.json) carries its operation surface as loaded data.
The [constraints contract](constraints/CONTRACT.md) specifies the supported Draft 2020-12 subset, local references, editable drafts, guidance limits, and checkpoint formats 3 and 4. Broader schema coverage, reusable definitions, and connected invocation contracts remain in the open register.
The [composition contract](composition/CONTRACT.md) specifies the first active definition format, context relationships, scalar command signatures, and mock instructions.

## Runtime behavior

**Maturity: bounded CLI-002 authoring and CLI-003 composition transitions are implemented and tested locally; broader runtime behavior remains provisional.**

An authoring session exposes unfinished work and pending validation findings.
An edit either produces its declared document transition or reports a failure whose mutation outcome is explicit.
Accepting a draft evaluates the applicable whole-document constraints under the selected policy.

The first slice explicitly selects unconstrained authoring.
Its `commit` copies candidate to accepted, while every accepted state-changing request durably checkpoints the session and its last receipt before acknowledgment.
Its `save` exports candidate bytes without changing acceptance or revision.
Failed edits preserve state, and uncertain checkpoint publication stops writes until reopening, as specified in the [persistence contract](authoring/SESSION-CONTRACT.md#persistence-and-export).

A definition is editable as data independently of whether it is active.
Activation selects an identified definition for subsequent discovery and invocation.
Operation availability and binding state are visible before invocation.
The composition profile retains active interface state separately from candidate and accepted documents, inside the existing checkpoint transaction.
Its `invoke` control resolves local command words from active data and records simulation-only outcomes.

An unbound operation has a discoverable contract without claiming executed functionality.
A mock returns explicitly simulated results under its declared behavior.
A connected operation reports the evidence and uncertainty that its actual capability supports.

Local document atomicity does not imply atomicity of external effects.
After interruption or a conflicting edit, the available record identifies known outcomes and unresolved uncertainty before a retry decision is justified.

## Verification obligations

**Maturity: provisional criteria; no runtime behavior is certified by this document.**

| Claim | Required observation |
|---|---|
| Precise authoring | Invalid edits, unusual keys, exact value types, array changes, and batch failures preserve the stated document guarantees. |
| Constraint fidelity | Accepted and rejected examples agree with the selected schema semantics, including supported references and unsupported features. |
| Interface consistency | Equivalent human and machine requests produce equivalent interpretation and observable results. |
| Definition integrity | Discovery, input handling, and dispatch agree on the same active operation model. |
| Honest mocking | Simulated outcomes remain distinguishable from real execution through capture, export, and resumption. |
| Resumability | A fresh actor continues from recorded artifacts and original requirements without the originating conversation. |
| Recovery | Interrupted and conflicting operations expose enough evidence to avoid guessing whether a mutation or effect occurred. |
| Reuse | Definitions produced for different purposes compose with explicit dependencies and visible incompatibilities. |

Independent evaluation against the original task tests meaning that a self-authored schema and mock cannot establish by agreement alone.
The [service-catalog task](authoring/acceptance/SERVICE-CATALOG.md) and [acceptance corpus](authoring/acceptance/authoring-cases.json) establish that independent first-slice input; [CLI-002](authoring/CLI-002.md) records actual application execution separately from the original design fixture.
The [working approach](approach.md) describes the experimental workflow without making its sequence part of this target instant.

## Axiom alignment and tensions

**Maturity: first-slice design audit complete; broader alignment remains preliminary.**

| Anchor | Alignment | Open tension or limit |
|---|---|---|
| A3 | Responsibility directories isolate a concern without publishing APIs. | The proposed dependencies require validation against concrete consumers before they become stable interfaces. |
| A4 | The complete source discussion is retained beside derived intent. | The exact resumption artifact must preserve decisions and evidence without requiring a full conversation dump at every invocation. |
| A5 | Both interaction audiences consume the same runtime meaning. | Local paired authoring, composition, and constraint trials exercise shared meaning; connected behavior remains untested. |
| A7 | Outcomes, interruption, and recovery are first-class requirements. | A behavior binding may be unable to determine an external outcome; such uncertainty must remain explicit. |
| A11 | Definitions and reusable deterministic operations carry mechanical work. | Total agent effort includes construction and repair; specification length alone is not the economic objective. |

The [dedicated CLI-001 audit](authoring/AXIOM-AUDIT.md) records `pass-with-guardrails` for the bounded authoring implementation.
It identifies required recovery, fidelity, declaration-integrity, and parity observations; a passing design audit is not a passing application test.
Broader reusable definitions, additional schema semantics, and connected behavior require their own concrete contracts and audit coverage. The first constraint subset has its [own audit](constraints/AXIOM-AUDIT.md).
The [CLI-003 audit](composition/AXIOM-AUDIT.md) covers the first definition and mock interpreter, including its exact-number boundary correction.

Correction, 2026-09-08: the previous A5 row said "application parity remains untested" after CLI-002 already retained passing application comparisons.
That stale claim is withdrawn; the table now separates the tested local slices from future capabilities.

## Mechanics, rationale, and consequence

**Maturity: provisional.**

### Mechanics

The registry declares the component scopes and semantic dependency graph.
Generated views carry that declaration into the anchored core and local responsibility records.
Open questions remain explicit until evidence or the owner's intent resolves them.

### Rationale

The scaffold gives an arriving actor a concrete structure to reason from while preserving the distinction between agreed purpose and proposed design.

### Consequence of violation

Treating provisional boundaries as settled APIs would hide the remaining design work.
Treating a target description as implemented reality would manufacture evidence that the scaffold does not contain.
